## Project overview

TORA DOS BURRO is a Discord-style real-time communication platform: servers/channels, roles/permissions, real-time chat, voice/video/screen-share over WebRTC, and Go Live (via LiveKit). Backend (Elixir/Phoenix): MVP (FASES 0-8) plus FASE 9 (Go Live) complete, **and deployed for real** on a VPS via Dokploy (`http://2.28.229.48`, no domain/TLS yet — see "Production deploy" below). Desktop client (React + Electron, `desktop/`): **FASE 11 is complete** — working auth, server/channel navigation (including joining an existing server via invite code), real-time chat, voice (real mesh WebRTC, with a real coturn TURN relay deployed on the VPS as NAT fallback alongside STUN — see below), screen share, video/camera, Go Live (LiveKit, client-side wired up — publish/subscribe of real media through an actual LiveKit server is still unverified, since this environment has no Docker), and a real Windows installer (`electron-builder`, NSIS, unsigned, no auto-update — download it built against production at `desktop/.env.production`). The actual single base server for this deploy ("TORA DOS BURRO") exists **on production**, owned by the real account `Ragazzo#4808` — an earlier copy created against the local dev database (owner `Ragazzo#9054`) is a different, unrelated record; don't confuse the two. Rust/C++/Python media services are planned for later and don't exist yet beyond empty placeholder directories (`rust/`, `cpp/`, `python/`).

### Production deploy

Backend runs on a VPS managed via [Dokploy](https://dokploy.com) (`http://2.28.229.48:3000/dashboard`, project `tora-dos-burro` — a separate, unrelated Dokploy project named "TORA" already existed there from an earlier, different attempt using a different repo ("Discord2"); leave it alone). Application service `backend` builds `backend/Dockerfile` (generated by `mix phx.gen.release --docker`, FASE 11 fatia 11) from this repo's `master` branch, build path `/backend`. A managed PostgreSQL service backs it. No domain yet — routed by Traefik via a bare-IP `Host()` rule on port 80 (`http://2.28.229.48`), so `config/prod.exs`'s `force_ssl` explicitly excludes that IP (see below) and the client's CSP/`.env.production` point at plain `http://`/`ws://`, not `https://`/`wss://`.

Four real, deploy-only bugs (never visible in `mix test`, `npm run typecheck`, or any local run):
- **`rel/overlays/bin/{server,migrate}` lost their Unix executable bit** — generated on Windows (no such concept there) and committed as `100644`. The container failed every single start with `exec: "/app/bin/server": permission denied`, straight from `runc`, before the BEAM ever got a chance to log anything — invisible in Dokploy's default ("Native") log view, only showed up after switching to "Swarm" mode logs. Fixed via `git update-index --chmod=+x`; watch for this again if release scripts are ever regenerated from Windows.
- **`force_ssl` in `config/prod.exs`** (present since the original `mix phx.new` scaffold, FASE 1, never revisited) redirected every plain-HTTP request to a `https://` that doesn't exist on this no-TLS deploy. Fixed by adding the VPS IP to the existing `exclude: [hosts: [...]]` list (same mechanism already used for `localhost`/`127.0.0.1`), not by disabling `force_ssl` outright — a future real domain would still get the redirect.
- **The "TORA DOS BURRO" server/invite tested during FASE 11 fatia 12 lived in the local dev Postgres**, not the VPS's fresh production database — completely different databases. The client pointed at production simply saw "invite not found." Recreated for real directly against production once noticed.
- **coturn crash-looped (exit 255) the first time it was deployed with every option passed as bare CLI flags** (`-n` + a long flag list, no mounted config file) — `docker-entrypoint.sh` execs `turnserver` with those args, and one of them didn't parse the way `getopt_long` expected, so turnserver dumped its entire `--help` text and exited, forever, on every restart. Fixed by moving almost everything into a mounted `turnserver.prod.conf` (parsed by coturn's own config-file parser, the same directives already proven fine in local dev since FASE 6) and reducing the CLI surface to a single override, `-c <path> --static-auth-secret=${TURN_SECRET}` — see `docker/coturn/docker-compose.prod.yml`.
- **Realtime (chat/voice, anything over `/socket`) from the packaged Electron client never actually connected against production** — every WebSocket handshake failed with HTTP 403, forever, invisible as anything other than a stuck "Conectando…" in the UI. Root cause: Phoenix's `check_origin` (default `true`, checks the `Origin` header against the endpoint's configured host) was never disabled in prod — only `dev.exs` has `check_origin: false`, and that's generic `mix phx.new` boilerplate, unrelated to this app's Electron client; nobody had actually joined a voice channel from the *packaged* app against the *real* VPS before (all earlier client-side realtime verification ran against `localhost:4000`/dev). Electron's packaged renderer (loading from `file://`) sends an `Origin` header that can never match the configured host, so it always failed this check specifically — a plain non-browser WebSocket client (no `Origin` header at all) sails through fine, which is why raw protocol tests never caught it. Fixed with `check_origin: false` on just the `/socket` transport in `endpoint.ex` (not `/live`) — `UserSocket.connect/3` already authenticates purely via a Guardian token in the query param, never a browser cookie, so the CSRF-style protection `check_origin` provides doesn't apply to this client at all. Found and fixed in `v1.0.3`.
- **Related hardening found investigating the same report**: the desktop client never refreshed its access token (15min TTL, `AuthController.tokens/1`) mid-session — only at boot. A long-lived voice/chat session whose socket ever needed to reconnect (network blip, a backend redeploy) would retry forever with the now-stale original token. Fixed in `v1.0.3`: `authStore.ts` refreshes every 10 minutes; `socket.ts`'s `Socket` now takes `params` as a function reading a mutable "current token" (`updateSocketToken`) instead of a value frozen at connect time, so any future reconnect — automatic or not — picks up whatever's freshest without tearing down a healthy connection to do it.

**coturn (TURN relay)**: deployed as its own Dokploy Compose service (`coturn`, Compose Type **"Docker Compose"**, not "Stack"/Swarm — this matters: it's what allows `network_mode: host` to work exactly like local dev, sidestepping Docker Swarm's routing-mesh limitations for the wide UDP relay port range TURN needs, RFC 5766 default `49152-65535`). Source: `docker/coturn/docker-compose.prod.yml` + `docker/coturn/turnserver.prod.conf` (both committed, no secrets in either — `TURN_SECRET` is set only in that Dokploy service's own masked Environment tab, written to a `.env` file next to the compose file on deploy and substituted into the `command:` override; must stay byte-identical to the `backend` service's own `TURN_SECRET`, both sides of the same REST-API HMAC). Verified with a hand-rolled STUN Binding Request (confirms the process is up and reachable) and a full long-term-credential TURN Allocate handshake using the exact credential algorithm from `ToraDosBurro.Turn` (confirms auth + relay allocation actually work) — both against the real public IP, not just container-internal checks. No `external-ip` needed (the VPS's network interface already carries the public IP directly, no NAT); no TLS (`no-tls`/`no-dtls`, same no-domain-yet reasoning as `force_ssl` above).

Also note: an interactive remote shell into the running production release (`bin/tora_dos_burro remote`) is blocked by the auto-mode safety classifier ("Sensitive Remote Exec") — for anything needing to act as a specific already-authenticated user in production, prefer reading that user's own already-issued token via `window.api.secureStorage.get('access_token')` from a real running client session and calling the REST API directly, rather than minting tokens through a remote console.

**One-off maintenance in production goes through `ToraDosBurro.Release`, never a Mix task.** The runner image (`backend/Dockerfile`'s final stage) only contains the compiled release — no `mix`, no source, no `pg_dump` (no Postgres client tools installed) — so anything meant to run against production has to be a public function in `lib/tora_dos_burro/release.ex` (wrapped in `Ecto.Migrator.with_repo`, same as the generated `migrate/0`), deployed first, then run by the user from Dokploy's terminal for the `backend` service as `/app/bin/tora_dos_burro eval 'ToraDosBurro.Release.<fun>(...)'`. Learned the hard way: a first "wipe all users" was written as `mix wipe_all_users` and would have failed with "mix: not found". Test such functions through a real local release (`mix release --overwrite` in dev, then `_build/dev/rel/tora_dos_burro/bin/tora_dos_burro.bat eval '...'` — use `~s(...)` instead of double quotes inside the expression, PowerShell mangles them), not just `mix run`. Current one: `wipe_users_except(keep, confirm: true)` — deletes every account but `keep` (`"user#1234"` or a discriminator matching exactly one account), transferring their servers to `keep` first; without `confirm: true` it's a dry run. The transfer is required, not optional: `servers.owner_id` is `null: false` despite `on_delete: :nilify_all`, so deleting any server owner outright makes Postgres reject the entire `DELETE` (`not_null_violation`) — the first version missed this because its test accounts owned no servers.

Read `README.md` first for current phase status, then `docs/*.md` (`architecture`, `database`, `api`, `realtime`, `media`, `security`, `roadmap`) — these are living design docs kept in sync with what's actually implemented, with explicit "Implementado" / "Ainda não implementado" notes where a feature is server-side-only so far.

## Development process — read before making changes

This repo follows a strict, user-mandated phased process (`docs/roadmap.md`), not ad hoc feature work:

1. Work proceeds one numbered FASE at a time, in the order listed in `docs/roadmap.md` — don't jump ahead or bundle multiple phases into one change.
2. **Before implementing anything, explain first**: objective, architecture, files involved, dependencies, data flow. Implement only after that's been laid out.
3. After implementing: add tests, then explain how to run and how to test it.
4. Don't invent APIs or libraries; verify real version compatibility (e.g. via `mix hex.info`) before adding any dependency, and justify why it's needed.
5. No premature microservices — Rust/C++/Python only get introduced when a phase has a concrete, measured need (see `docs/architecture.md` for the "why not TypeScript, why not Rust" justification bar).
6. Control Plane / Media Plane / Data Plane stay strictly separated (see Architecture below).

This project has consistently been built feature-by-feature with tests and a live/manual check at each step, not in large bulk changes — keep following that pattern rather than batching work across phases.

## Architecture

### Three planes

- **Control Plane** (`backend/lib/tora_dos_burro/` contexts + `backend/lib/tora_dos_burro_web/` controllers/channels): auth, users, servers, roles/permissions, channels, messages, presence, WebRTC *signaling only*.
- **Media Plane**: real audio/video/screen-share bytes, via WebRTC (DTLS-SRTP) — **never** touches the Phoenix WebSocket. Phoenix Channels only relay SDP offers/answers and ICE candidates as opaque JSON (or, for Go Live, just hand out a LiveKit token — no SDP/ICE relay at all, since the SFU handles that). Client-side peer connections are real for voice (audio), video (camera), and screen share — all three share the same mesh (`desktop/src/renderer/src/webrtc/MeshManager.ts` — see "Desktop client" below). Go Live is a separate, non-mesh connection straight to LiveKit via the official `livekit-client` SDK (`desktop/src/renderer/src/stores/goLiveStore.ts`) — client-side join/token/error-handling flow is wired up and live-verified, but actual publish/subscribe of media through a running LiveKit server is still unverified (no Docker in this environment). See `docs/media.md` ("Fluxo do Go Live").
- **Data Plane**: PostgreSQL (`Ecto`/`Repo`) for durable state, `Phoenix.Presence` for all ephemeral realtime state (below), object storage (planned, MinIO/S3) for attachments.

### Contexts (`backend/lib/tora_dos_burro/`)

- `Accounts` — registration/auth. Usernames are **not** globally unique alone: identity is Discord-style `username#discriminator`, with a unique index on the pair and randomized-with-retry discriminator assignment on collision (`insert_with_discriminator/2` in `accounts.ex`) — kept exactly as-is by explicit user decision (asked whether to enforce unique usernames instead; chose to keep duplicates allowed). `email` is optional (`null: true`, migration `make_user_email_optional`) — the client only collects username+password, never email. `POST /auth/login` has two clauses: `{username, discriminator, password}` (original, exact) and `{username, password}` (the common path now — `Accounts.authenticate_user/2`, no discriminator). The 2-arg path looks up every user with that username: zero matches → timing-safe `:unauthorized` same as always; exactly one → normal password check; two or more → `:ambiguous_username` (422), telling the client to retry against the 3-arg clause with a discriminator — it deliberately never tries the password against multiple candidates to guess which account, since two people sharing a username could coincidentally also share a password. Registration also auto-joins the account to `Application.get_env(:tora_dos_burro, :default_server_id)` if configured (`AuthController.register/2` → `Servers.join_server/2`, which already existed, then `Servers.notify_member_joined/3` — `v1.6.0`, see `Servers` below) — the single-server "no invite needed" flow; unset (dev/test) or pointing at a missing server is a silent no-op, never fails registration. Login is still the rare recovery path (not the normal flow — the desktop client persists the session locally via `safeStorage`), just simpler now.
- `Guardian` — JWT (access + refresh), backed by `guardian_db` for revocation/rotation (plain Guardian is stateless and can't revoke on its own).
- `Servers` — servers, members, roles, invites, bans; owns `effective_permissions/2` (server-level) and `authorize/3`. `notify_member_joined(server, member, user)` (`v1.6.0`, bug fix — see `serversStore`/`presenceStore` below) broadcasts `member:joined` on `server:{id}` (the same topic `ServerChannel` already uses for online presence) so clients watching that server pick up a new member live, instead of only on the next server-reselect. Deliberately **not** inside `join_server/2`/`do_add_member` (the actual DB insert) — `use_invite/2` calls `join_server/2` from *inside* a `Repo.transaction`, and a broadcast fires immediately, not on commit; if it lived in `join_server` a later rollback in that same transaction (e.g. a banned user, only caught by `join_server` itself mid-transaction) would still have told every watcher someone joined who, in the database, never actually did. Both real callers (`use_invite/2`, after the transaction returns `{:ok, _}`; `AuthController.register/2`'s auto-join, which never runs inside a transaction) call it only once the join is durably committed.
- `Servers.Permissions` — the permission bitfield (`view_channels`, `send_messages`, `manage_roles`, `administrator`, etc. — see the module for the full flag list and hex values).
- `Channels` — channels, categories, `permission_overwrites`. Owns the Discord-equivalent per-channel permission resolution in `channel_permissions/3`/`authorize/3`: server base → `@everyone` overwrite → other role overwrites → member-specific overwrite → `administrator` bypasses overwrites entirely → server owner always passes regardless of role. This exact order is load-bearing.
- `Chat` — messages, reactions. Ordering/pagination uses a monotonic `seq` (bigserial) column, **not** `inserted_at`/id — timestamps aren't a reliable order key here (UUID PKs aren't sortable, and OS clock resolution, observed concretely on Windows, isn't fine-grained enough to break same-millisecond ties). Don't revert this to timestamp-based ordering.
- `GoLive` — issues LiveKit access tokens (`GoLive.LiveKitToken`, hand-rolled JWT via `joken`, not the stale/partial third-party `livekit` hex package). No Room Service API calls — a LiveKit room auto-creates on first authenticated join. `start_stream/2` (needs `:stream`, publisher token) and `watch_stream/2` (needs `:connect`, subscriber-only token) both delegate to `Channels.authorize/3` — same permission machinery as everything else, nothing new.

### Realtime (`backend/lib/tora_dos_burro_web/channels/`)

- `UserSocket` authenticates via a Guardian token passed as a **connect param** (`?token=`), not a header — browsers can't set custom headers on the WS handshake.
- `ChatChannel` (topic `channel:{id}`) — text chat: `message:create/update/delete/reaction`, `typing:start/stop`. Mutations happen over the socket, not REST; REST only covers CRUD-ish resources and history pagination (`docs/api.md`).
- `VoiceChannel` (topic `voice:{id}`) — voice/video/screen-share signaling: `sdp:offer`/`sdp:answer`/`ice:candidate` relay (broadcast + client-side `to`/`from` filtering — mesh topology, fine at small scale), `state:update` (mute/deafen), `video:enable/disable`, `screen_share:start/stop`. Camera is server-enforced, never client-trusted: max 4 concurrent video participants per channel. Screen share has **no concurrency limit** — deliberately reverted post-`v0.15.0` at the user's request, since this deploy is a single, private, ~20-person server, not the "large public room" scenario the original 1-at-a-time limit assumed; the underlying cost (every simultaneous screen share is one more video track every mesh peer decodes) is still real and wasn't solved, just accepted for this specific scope — don't generalize this to a public or larger-room deploy without revisiting. See `docs/media.md` ("Limites do mesh").
- `GoLiveChannel` (topic `live:{id}`, FASE 9) — Go Live via LiveKit (SFU), channel must be `guild_voice`. `join` returns a subscriber-only token; `golive:start` elevates to a publisher token (checked at that point, not just at join — same pattern as `video:enable`); `golive:stop` reverts. Deliberately **no** cap on simultaneous streamers per room, unlike FASE 8's screen-share — that limit exists because of mesh fan-out cost, which doesn't apply once an SFU is involved, so don't add one here without a real reason.
- `ServerChannel` (topic `server:{server_id}`, `v1.2.0`) — presence-only, app-wide "who's online" (not "who's in a voice call," that's still `VoiceChannel`'s own Presence, scoped to one room). No client→server events at all, just `join` (membership-checked the same way as everywhere else, `Servers.fetch_member/2`) + `Presence.track`. Since `v1.6.0`, this same topic also carries a one-way server→client `member:joined` broadcast (from `Servers.notify_member_joined/3`, not something the channel process itself sends — a plain `Endpoint.broadcast` reaches any process subscribed to the topic, channel or not) — see `serversStore`/`presenceStore` below for why. The desktop client joins it once per selected server (`presenceStore.ts`, from a `HomePage.tsx` effect on `selectedServerId`) and leaves it on logout; it's what backs the member list in the right-hand `MemberList.tsx` panel. **Voice-channel occupancy (`v1.8.0`)** also rides this topic: `VoiceChannel`'s `after_join` does a second `Presence.track(self(), "server:#{channel.server_id}", user_id, %{voice_channel_id: ...})` — same `user_id` key as `ServerChannel`'s own `%{online_at: ...}` meta, so a user in a call just has two metas under one key (the online set is unchanged: still "any key present"). Tracking the `VoiceChannel` *process* (not the socket's `ServerChannel`) means leaving the call or dropping the connection untracks it automatically, no explicit cleanup. Deliberately **no** `Presence.update` on this topic for mute/deafen/etc. — each update is a leave+join diff, and bursts of those are exactly what produced out-of-order diffs before (see `MeshManager` below); occupancy only needs track/untrack. Not permission-filtered per recipient: every server member receives every voice channel's occupancy — fine today because `Channels.list_channels/1` doesn't filter by `view_channels` either (everyone already sees every channel), but must be revisited if hidden channels are ever added.
- `ToraDosBurroWeb.Presence` backs **all** ephemeral state (who's in a voice room, muted/deafened/video/screen-share/live flags, and now who's online app-wide) — deliberately never persisted to Postgres; it's session state, not history.
- Every `join/3` re-authenticates (Guardian) and re-authorizes (roles + `permission_overwrites`) — never trust a client-asserted permission.

### IDs

Every table uses `binary_id` (UUID) primary keys.

## Desktop client (`desktop/`)

React + Electron + TypeScript, built with `electron-vite` (three build targets, one config block each in `electron.vite.config.ts`):

- `src/main/` — the only place with real Node/Electron access: window creation, secure token storage (`safeStorage`, IPC handlers `secure-storage:*`), permission gating (`session.setPermissionCheckHandler`/`setPermissionRequestHandler` — only `'media'`/`'display-capture'` allowed, everything else denied by default), screen-share source listing (`desktopCapturer`) and `setDisplayMediaRequestHandler`.
- `src/preload/` — thin `contextBridge` bridge (`window.api.{secureStorage,screenShare}`), nothing else. **Must build as CommonJS** (`output: { format: 'cjs' }`, set in its `electron.vite.config.ts` block) — `sandbox: true` (in `main/index.ts`'s `webPreferences`, deliberately never turned off) flatly refuses an ESM preload with `SyntaxError: Cannot use import statement outside a module`, and it fails *silently in the window's own console*, not the terminal — this went unnoticed through several phases because every earlier check ran the renderer's Vite dev server in a plain browser tab (no preload there either way, so a missing `window.api` looked "expected"). If `window.api` is ever undefined inside the real app, check the preload's output format first.
- `src/renderer/` — the React app (`src/renderer/src/`), Tailwind v4 (`@tailwindcss/vite`), Vite dev server on port 5173 in dev. `index.html`'s CSP `connect-src` must cover every host the renderer actually connects to — it's the same kind of silent, terminal-invisible failure as the preload CJS gotcha above (a blocked `connect-src` shows only as a `securitypolicyviolation`/console error inside the real window, and the resulting network failure looks identical to "server unreachable" to application code, since browsers deliberately don't expose *why* a WebSocket failed to JS). Found live while wiring up Go Live: LiveKit's URL is delivered dynamically by the backend at runtime (never known at build time), so it's allowed by scheme (`ws:`/`wss:`/`http:`/`https:`, not by host) — and `livekit-client` needs both a WebSocket *and* an HTTP preflight (`.../validate`) allowed to the same host, discovered only by fixing one and still seeing the other blocked.

Visual identity (`v1.0.4`, `src/renderer/src/index.css`): a deliberate "rig"/HUD look, not a Discord-purple reskin — tokens defined via Tailwind v4's `@theme` (`--color-void/panel/panel-2/line`, `--color-volt` lime-green for positive/active state, `--color-plasma` magenta for hot/live/danger state — two accents with distinct meaning, not one generic neon color), `Chakra Petch`/`Manrope`/`JetBrains Mono` for display/body/technical text (loaded via a `<link>` in `index.html`, not a CSS `@import` — that broke Lightning CSS's `@import`-must-be-first rule in the production build only), and a signature top-right bevel cut (`.bevel`/`.bevel-sm`/`.bevel-lg` utilities, `clip-path`) on large surfaces only (cards, panels, primary buttons — never small elements like reaction pills, where it'd just be noise). The one signature moment: in `VoicePanel.tsx`, an unmuted participant's tile gets a pulsing volt glow ("hot mic") — tied to real call state, not pure decoration. `index.html`'s CSP needed `style-src`/`font-src` additions for `fonts.googleapis.com`/`fonts.gstatic.com`, same class of gotcha as the LiveKit `connect-src` one above.

Window chrome (`v1.0.6`): frameless (`frame: false` in `main/index.ts`'s `BrowserWindow`) — no native title bar/menu-adjacent buttons at all, "borda infinita" per the user's request. `components/TitleBar.tsx` draws 100% of it (wordmark + minimize/maximize-restore/close, inline SVG icons, matching the volt/plasma/bevel system) and drives real window actions through new `window.api.windowControls.*` IPC (`minimize`/`toggleMaximize`/`close`/`isMaximized`/`onMaximizeChanged`) — the renderer can never call these directly, only the main process owns the `BrowserWindow`. Maximize state is pushed to the renderer via `win.on('maximize'/'unmaximize', ...)`, not just toggled client-side on click, so it stays correct after a double-click on the drag region, Aero Snap, or anything else that changes it outside the button itself. The drag region and its button cutouts are plain CSS (`app-drag`/`app-no-drag` utilities in `index.css`, i.e. `-webkit-app-region`) — verifying any of this needs the real window (`GetWindowRect`/`CopyFromScreen` from PowerShell, or similar), never the Browser pane or `Page.captureScreenshot` over CDP, since native chrome (or its absence) isn't part of the page's own DOM.

System tray (`v1.2.0`, user-requested): the ✕ button (and `Alt+F4`/anything else that fires the window's `close` event) no longer quits — `main/index.ts`'s `win.on('close', ...)` calls `event.preventDefault()` and `win.hide()` instead, unless a module-level `isQuitting` flag is set, so the app keeps running (and any active voice call keeps working — Chromium doesn't suspend `getUserMedia`/WebRTC for a hidden-but-not-destroyed window, only a truly closed one) with just a tray icon left. `isQuitting` is set in exactly two places: the tray context menu's "Sair" item, and an `app.on('before-quit', ...)` handler that catches every *other* real quit path too (so nothing but an actual quit request can ever get stuck unable to close). Fixes both symptoms at once, since both read from the same now-live `serversStore.members`: the voice/chat roster no longer shows "desconhecido" for someone who joined after the initial fetch, and `MemberList.tsx` no longer drops them from both Online *and* Offline (they were invisible, not just miscategorized, since the cross-reference requires being in `members` at all). Verified live against the real backend with two real accounts, no fake data and no second Electron instance needed: one already had the server open, the other registered and redeemed an invite via plain `curl` — the new member appeared in the first client's sidebar immediately, no reselect, no reload.

`services/socket.ts` holds one `phoenix` (npm package, same version as the backend's Phoenix) `Socket` per authenticated session. `webrtc/MeshManager.ts` is the WebRTC mesh: one `RTCPeerConnection` per participant, **perfect negotiation** (polite/impolite by comparing `user_id` strings — both sides compute the same comparison, so they always agree on who's who) so simultaneous offers don't corrupt signaling state, plus a queue for ICE candidates that arrive before `setRemoteDescription` resolves. Video (camera), screen share, and screen-share audio (`v1.4.0`) reuse the *same* peer connections as voice — not a second mesh — and each other: `setCameraTrack`/`setScreenTrack`/`setScreenAudioTrack` create their `RTCRtpSender` **lazily** (only the first time that slot is actually turned on, via `addTrack`) and from then on only ever call `replaceTrack` (never `removeTrack`), specifically to avoid renegotiating during the glare-prone moment right after two peers discover each other — pre-creating both video transceivers upfront was tried and broke exactly there (see `docs/media.md`, "Fluxo de vídeo", for the full story). Since there's no fixed transceiver per slot, an incoming video (or, since `v1.4.0`, audio) track doesn't say on its own whether it's camera-vs-screen (or mic-vs-screen-audio) — `voiceStore.ts` disambiguates using what Presence already reports for that peer (`video`/`screen_sharing`/`screen_sharing_audio`), which always arrives before the track itself. Every signaling event carries `to`/`from`; the client must filter on `to === currentUserId` since the server broadcasts to the whole topic, not just the addressee. `presence.onLeave` deliberately does **not** tear down a peer connection — `Phoenix.Presence.handle_diff/2` computes each diff in its own async `Task`, and a burst of metadata updates (mute/deafen/video/screen_sharing, all `Presence.update`) close together can have those tasks resolve out of order, making the client see a "leave" with no join yet applied for someone who never actually left. Tearing down the connection on that phantom leave corrupted the next negotiation for real (confirmed live). A peer connection now only gets torn down on its own `connectionstatechange` going `failed`/`closed` — slower to notice a genuine departure, but never a false positive.

Screen-share source picking has no native picker on Windows (Electron's `useSystemPicker` is macOS-15+-only), so `components/ScreenSharePicker.tsx` is hand-built from `desktopCapturer.getSources()` thumbnails: user picks a source → renderer tells `main` which one via `window.api.screenShare.selectSource(id)` → renderer calls `getDisplayMedia()`, which triggers `setDisplayMediaRequestHandler`, already primed to resolve with that source. The server-side exclusivity claim (`screen_share:start`) happens *after* the user already picked a source, not before, so losing the race doesn't waste a picker interaction.

**Audio limiter on captured system audio (`v1.7.0`, user-reported "audio estourando"/clipping)**: `webrtc/audioLimiter.ts`'s `limitAudioTrack(track)` routes a captured `MediaStreamTrack` through an `AudioContext` (`MediaStreamAudioSourceNode` → aggressive `DynamicsCompressorNode`, threshold -18dB/ratio 16/attack 3ms — broadcast-limiter settings, not gentle compression → `MediaStreamAudioDestinationNode`) and returns the processed output track plus a `cleanup()` closing the context. Root cause it addresses: the Windows mixer sums everything currently rendering (game, music, and — since `v1.6.0` stopped muting the broadcaster's own call audio — their own voice too) with no level control before this app published it raw, easily exceeding 0dBFS. Wired into both places that publish loopback-captured audio: `goLiveStore.ts`'s `startGoLive` (simple — LiveKit publishes tracks directly, so the raw track is just swapped for the limited one, tracked in module-level `publishedAudioTrack`/`audioLimiterCleanup` since `stopGoLive` needs the exact published-track reference to `unpublishTrack`) and `voiceStore.ts`'s `startScreenShare`/`updateScreenShareQuality` (trickier — the processed track has to stay inside the *same* `MediaStream` object as the screen's video track via `stream.removeTrack`/`addTrack`, not a new one, to preserve the msid-based grouping `MeshManager` has relied on since `v1.4.0` for merging screen video+audio on the receiving end; the raw track is deliberately kept alive, un-stopped, after being removed from the stream — it's still feeding the Web Audio graph — and only actually stopped, alongside closing the context, via a module-level `screenAudioLimiter`/`stopScreenAudioLimiter()` called from every place that already tore down screen share: `stopScreenShare`, before each quality-change recapture, and `leave()`). Verified live against a real synthetic tone (not the real loopback path — blocked by the same hardware limitation documented since `v1.3.0` on this test machine): `limitAudioTrack` returns a distinct, live track that carries real, non-zero-RMS audio, confirming the source → compressor → destination pipeline itself works, even though the full loopback-capture path couldn't be exercised here.

**Configurable global mute/deafen shortcuts (`v1.7.0`, user-requested)** — `globalShortcut` (Electron main-process API), deliberately not a renderer `keydown` listener: they need to fire even when the window is unfocused or minimized to the tray, the main scenario for wanting this at all (gaming with the app backgrounded). `main/index.ts`'s `registerShortcutHandlers` exposes `shortcuts:set` (unregisters the previous accelerator for that action, registers the new one, reports back whether `globalShortcut.register` actually succeeded — it fails silently if the combo is already claimed by another program) and forwards a real trigger to the renderer via `shortcuts:triggered`. The renderer owns the actual keybinding *preference* (main has no access to the renderer's `localStorage`): `settingsStore.ts` gained a `shortcuts: {mute, deafen}` field (same persisted object/key as mic settings and `soundCuesEnabled`, defaults `Control+Shift+M`/`Control+Shift+D`) whose `loadForUser` pushes both to main via IPC on login, and a `setShortcut(action, accelerator)` action that calls `window.api.shortcuts.set` *first* and only updates/persists state if that resolves `{ok: true}` — never stores a binding that didn't actually register. `SettingsModal.tsx`'s new `ShortcutRecorder` puts a button into "recording" mode on click, captures the next `keydown` (`capture: true`, `Escape` cancels), and converts it to an Electron Accelerator string via `eventToAccelerator` — deliberately rejects any combination with zero modifier keys (`Control`/`Alt`/`Shift`/`Super`), since a bare-key *global* shortcut would hijack that key from every other program on the system for as long as this app is running. `HomePage.tsx` listens for `shortcuts:triggered` and calls `toggleMute`/`toggleDeafen`, guarded by `useVoiceStore.getState().status === 'connected'` (a no-op otherwise) — the existing mute/unmute identification sounds (`v1.5.0`) already double as the only feedback needed that a background keypress landed, no new UI required. `app.on('will-quit', () => globalShortcut.unregisterAll())` releases the OS-level reservations on exit. Verified live: real `KeyboardEvent` (not `element.click()`) correctly captured and converted to `"Control+Shift+K"`, and the setting only persisted after a genuine `{ok: true}` round-trip through `globalShortcut.register` in the real main process — confirming registration itself works. **Not verified**: physically pressing the registered combo — there's no way to simulate a true OS-level global keypress via CDP (only in-page events), so the remaining leg (`globalShortcut`'s callback → IPC → `toggleMute`) rests on trusting a one-line, standard Electron API call on each end rather than a live click-through.

**Update notification system (`v1.7.0`, user-requested "não precisar ficar rebaixando toda hora")** — not `electron-updater`: the installer is unsigned, so a fully silent auto-download-and-replace would trip the same SmartScreen "unknown publisher" warning as a manual install, just at a more confusing moment (mid-background-update) to explain to someone just trying to stay in a call. Instead, `main/index.ts` polls the public, unauthenticated `GET api.github.com/repos/PedroRagazzo/personal-communication/releases/latest` (5s after boot, then every `UPDATE_CHECK_INTERVAL_MS` — the app can sit in the tray for days, `v1.2.0`, so a boot-only check would miss anything released meanwhile) and compares `tag_name` against `app.getVersion()` via a small hand-rolled `compareVersions` (three dot-separated numbers — not worth a `semver` dependency). A newer version sends `updates:available` (version, release page URL, the `-setup.exe` asset's `browser_download_url`, filename) to the renderer's `updatesStore.ts`, which drives a `TitleBar.tsx` icon (`UpdateIndicator` — the *only* thing always mounted regardless of auth state, per `App.tsx`, hence where `updatesStore.init()` is called, so the check runs even on the login screen) cycling through idle → downloading → downloaded/error. Downloading (`updates:download`) uses `webContents.downloadURL` + `session.defaultSession`'s `will-download` event with `item.setSavePath(...)` set explicitly (not `setSaveDialogOptions`) to save straight to `app.getPath('downloads')` with zero dialogs — Windows' native taskbar progress shows up on its own, standard `DownloadItem` behavior. Once downloaded, the icon becomes an "install" button (`shell.openPath` on the saved `.exe` — the person just confirms the same unsigned NSIS wizard they already know from the original install); a download error falls back to an "open in browser" button (`shell.openExternal` on the release page) so there's always some path to the new version. **This is *why* the GitHub repo went public in `v1.7.0`** (previously private) — asked and confirmed with the user first: a private repo's release assets need GitHub auth to fetch at all, and the only alternatives were embedding a token in the distributed app (real secret-leak risk — trivially extractable from the packaged `.asar`) or turning the VPS into a ~115MB-binary download proxy (real new infrastructure for what was asked as "just show an icon"). Public sidesteps both. Verified live end-to-end against the real, now-public repo: temporarily forced `app.getVersion()` down to `1.0.0` to exercise the "update available" path, watched the real icon appear (`⬆ v1.6.0`), clicked through a real download (confirmed the ~115MB file landed in Downloads, byte-identical size to the original build), and the icon correctly flipped to "Instalar v1.6.0" — stopped short of actually clicking that (would open a real NSIS installer on the test machine for no additional signal, since `shell.openPath` is a one-line call). **Repo renamed `tora-dos-burro` → `personal-communication` shortly after `v1.7.0` shipped** (user-requested, `gh repo rename`, which also updated the local `origin` remote automatically) — `GITHUB_REPO` and every doc reference updated to match. Confirmed live (not assumed) that this doesn't strand the already-shipped `v1.7.0` installer: GitHub 301-redirects `api.github.com/repos/{old}/releases/latest` to the new repo's real release data, and `fetch`'s default `redirect: "follow"` behavior means the old hardcoded constant baked into that installer keeps resolving correctly with no forced re-download required — verified with a direct `curl` against the old API path, not inferred from GitHub's general renamed-repo docs.

**Direct "join stream" button on the voice roster (`v1.7.0`, user-requested)** — the participant list in `VoicePanel.tsx` already showed a plain-text "● LIVE" badge for anyone broadcasting; reaching their stream required scrolling down to the separate `GoLiveStreams` card. That badge is now a real button (for anyone other than yourself) toggling between "● ENTRAR" and "● ASSISTINDO", calling the *exact same* `watchStream`/`stopWatchingStream` actions the card already used — a second entry point, not a replacement, built entirely from already-proven primitives (low enough risk that it didn't get a dedicated live test this round, unlike everything else in `v1.7.0`).

**Call audio lives outside `VoicePanel` + persistent voice bar (`v1.8.0`, user-requested)**. Found while building the bar: the call's `<audio>` elements (each participant's mic) used to be rendered *inside* `VoicePanel.tsx`, which `HomePage.tsx` only mounts while a voice channel is selected — so opening a text channel mid-call silently unmounted them and you stopped hearing everyone (while they kept hearing you). Moved to `components/CallAudio.tsx`, mounted unconditionally by `HomePage.tsx` (renders nothing when `remoteAudioStreams` is empty); it also exports `clampVolume` (moved with it — `RemoteVideo` in `VoicePanel` still uses it). Screen share / Go Live `<video>` tiles deliberately stay in `VoicePanel` — leaving that view hiding them is expected. `components/VoiceStatusBar.tsx` is passed to `ChannelList` as its `footer` prop and renders whenever `voiceStore.status !== 'idle'`: connected/connecting state, AO VIVO/🖥️ badges if you're live or sharing, the channel name (click → `selectChannel`, back to the call view), and mute/deafen/SAIR (SAIR = `voiceStore.leave()` + `goLiveStore.leave()`, same as `VoicePanel`'s own button). Verified live in the real Electron window against the real backend, with a second real account joining/leaving via a plain Node `phoenix` client (no second Electron instance needed — occupancy is signaling-only): the second account showed up under the voice channel ~1s after joining, both when it was already there before the server was opened (initial `presence_state`) and when it joined while watching (`presence_diff`), and disappeared right after leaving. For the bar: joined voice via a real sidebar click, injected a silent synthetic `MediaStream` into `remoteAudioStreams` as a fake partner, clicked into a text channel — `VoicePanel` gone, the `<audio>` element still there playing that same stream; mute/deafen via the bar changed store state (and deafen muted the element); clicking the channel name returned to the voice view; SAIR took both stores to `idle` and removed the bar and the audio element.

## Testing

- Backend: ExUnit + `Phoenix.ConnTest`/`ChannelTest`, via the support cases in `backend/test/support/`: `ConnCase`, `DataCase`, `ChannelCase`.
  - A Channel test that closes a socket with `close/1` must set `Process.flag(:trap_exit, true)` first — the channel process is linked to the test process, and without trapping exits the test crashes instead of asserting on the resulting `presence_diff`.
- Desktop client: `npm run typecheck` only — no automated test suite exists yet for `desktop/`. Real-app verification has been manual but thorough (see below).
- Convention so far has been to verify realtime/media features against the real running app, not static checks alone: a real WebSocket client (Node + the actual `phoenix` npm package) for backend-only phases; for client phases, driving the actual renderer via dynamic `import()` of the store modules plus a forced auth state, which works from any Chromium context *including* the plain browser pane.
- **`window.api` (secureStorage, screenShare, anything preload-provided) only exists inside the real Electron window — never in a plain browser tab.** To reach the real Electron window's own console for verification: launch with `electron-vite dev --remoteDebuggingPort <port>`, then drive it over the Chrome DevTools Protocol (`Runtime.evaluate` against the target's `webSocketDebuggerUrl` from `http://localhost:<port>/json/list`; Node's built-in `WebSocket` global is enough, no extra dependency needed). This is how the sandboxed-preload-needs-CJS bug (see "Desktop client" above) was actually found — it was invisible from outside a real Electron window.
