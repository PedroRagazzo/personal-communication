# Roadmap por fases

Regra fundamental: **não avançar para uma fase sem verificar se a anterior está funcional.** Cada fase é uma resposta explicando objetivo/arquivos/arquitetura/dependências/fluxo de dados **antes** de implementar (ver processo de desenvolvimento abaixo).

```
FASE 0  → Arquitetura                        [CONCLUÍDA]
FASE 1  → Backend básico (Phoenix, health check)                        [CONCLUÍDA — v0.1.0]
FASE 2  → Autenticação (Guardian, argon2id, guardian_db)                [CONCLUÍDA — v0.2.0]
FASE 3  → Usuários e servidores (roles, permissões, convites, bans)     [CONCLUÍDA — v0.3.0]
FASE 4  → Chat em tempo real (núcleo — anexos leves pendentes)          [NÚCLEO CONCLUÍDO — v0.4.0-core]
FASE 5  → Canais (categorias, permissões por canal)                    [CONCLUÍDA — v0.5.0]
FASE 6  → Voz (mesh WebRTC, sinalização, Presence)                     [CONCLUÍDA — v0.6.0]
FASE 7  → Vídeo (câmera, MediaSession, cap de 4 participantes)         [CONCLUÍDA — v0.7.0]
FASE 8  → Compartilhamento de tela (desktopCapturer)                   [CONCLUÍDA — v0.8.0, cap revisado após v0.15.0]
──────────────────────────────────────────── fim do MVP (backend) ────
        → Amigos / Mensagens Diretas (schema já pronto na FASE 3/4)     [FORA DE ESCOPO — ver item 8]
FASE 9  → Go Live (SFU: LiveKit — ver media.md)                        [CONCLUÍDA (backend) — v0.9.0]
FASE 10 → Arquivos — gestão avançada (redefinida, ver nota abaixo)     [FORA DE ESCOPO — ver item 8]
FASE 11 → Cliente Electron (empacotamento, distribuição)          [CONCLUÍDA — v0.17.0]
FASE 12 → Rust (media services — redirecionado pela adoção de SFU na FASE 9, ver media.md)
FASE 13 → C++ (media engine nativo, chamado a partir do Rust)
FASE 14 → Python / Machine Learning (analytics, moderação automática)
FASE 15 → Escalabilidade (libcluster, Redis PubSub adapter, SFU independente)
FASE 16 → Segurança (hardening de produção, gestão de segredos, TLS real no coturn)
FASE 17 → SDK (Rust primeiro, depois bindings)
FASE 18 → Testes e produção                    [EM ANDAMENTO — deploy em VPS via Dokploy, v1.0.8]
```

**"MVP (backend)" concluído** com a FASE 8 (`v0.8.0`): 68 testes passando, cada
fase verificada de ponta a ponta (incluindo com clientes WebSocket reais, não
só a suíte automatizada). O qualificador "(backend)" importa — FASES 6, 7 e 8
implementaram toda a sinalização/autorização/Presence do lado do servidor,
mas a metade client-side (peer connections WebRTC de verdade, perfect
negotiation, STUN/coturn, `desktopCapturer`) depende do Electron e só entra
na FASE 11. Sem um cliente de verdade, ninguém liga microfone/câmera/tela
ainda — só o "esqueleto" que torna isso possível está pronto.

Pendente antes de um MVP completo de ponta a ponta: anexos leves (FASE 4,
precisa de Docker/MinIO) e verificação de mídia real do Go Live contra um
LiveKit rodando (FASE 9, também precisa de Docker). Amigos/DM segue fora de
escopo por decisão do usuário (fast-follow abaixo, não planejado). A FASE 11
(cliente Electron, incluindo empacotamento) está **concluída** (`v0.16.0`).

## Correções registradas em relação ao documento original

1. **Anexos de arquivo**: o documento original lista "Uploads" como FASE 10 (depois do Go Live). Anexos **leves** (imagem/arquivo pequeno, com validação) entram na **FASE 4** — chat sem nenhum anexo não é utilizável, e isso evita que a FASE 4 fique "funcional" apenas parcialmente. A FASE 10 passa a significar **gestão avançada de arquivos** (arquivos grandes, upload retomável, cotas, CDN) — um endurecimento pós-MVP, não a introdução do recurso básico.
2. **Amigos/DM**: não aparecia como fase explícita no documento original (schema de `server`/`channel` sugeria isso implicitamente). Fica registrado aqui como **fast-follow logo após a FASE 8** (fora do MVP formal, mas antes da FASE 9), já que o schema (`friend_requests`, `channels.type = dm/group_dm`, `channel_recipients`) é desenhado desde a FASE 3/4 para suportar isso sem retrabalho. **Fora de escopo pra este deploy** (ver item 8) — o schema continua pronto se um dia fizer sentido, mas não é trabalho planejado.
3. **FASE 9 (Go Live)**: decisão de SFU resolvida no kickoff da fase — **LiveKit**, não mediasoup (a recomendação preliminar original) — ver `media.md` para o raciocínio completo. Backend (autorização + emissão de token) implementado e verificado; o lado cliente/mídia real depende do LiveKit rodando (sem Docker neste ambiente) e do Electron (FASE 11).
4. **FASE 11 (Electron)** é grande demais pra uma fatia só (Regra 1) — sendo dividida em fatias dentro da própria fase, cada uma com seu próprio ciclo explicar → implementar → testar: **fatia 1** (scaffold + autenticação, `v0.10.0`), **fatia 2** (lista de servidores/canais — navegação só leitura, `v0.11.0`, trouxe também o `GET /api/v1/servers` que faltava no backend), **fatia 3** (chat em tempo real — socket, histórico + `message:create` ao vivo, `v0.12.0`), **fatia 4** (voz — mesh WebRTC de verdade com perfect negotiation, `v0.13.0`), **fatia 5** (compartilhamento de tela — `desktopCapturer`, `v0.14.0`, ver `media.md`), **fatia 6** (vídeo/câmera — `v0.15.0`, ver `media.md`), **fatia 7** (deafen — `v0.15.2`, ver `media.md`), **fatia 8** (editar/apagar/reagir mensagem — `v0.15.3`, ver `realtime.md`) e **fatia 9** (criar canal — `v0.15.4`) concluídas; entre a 5 e a 6, o fluxo de autenticação foi simplificado a pedido do usuário (cadastro só usuário+senha, login por `username#discriminator`+senha como caminho de recuperação — sessão persiste sozinha depois do primeiro login, `v0.14.1`, ver `api.md`/`database.md`/`security.md`); logo após a 6, o cap de tela foi revisado (item 7 abaixo, `v0.15.1`). A fatia 8 também expôs `message:reaction:remove` no Channel, evento novo — `Chat.remove_reaction/3` já existia no contexto desde a FASE 4 mas nunca tinha sido exposto. A fatia 9 não mudou nada no backend (`POST /servers/:id/channels` já existia e já era testado desde a FASE 4/5) — só ligou o cliente: form inline na `ChannelList` (nome + tipo texto/voz), qualquer membro vê o botão, servidor sempre revalida `manage_channels` (sem checagem de permissão replicada no cliente, mesmo padrão de vídeo/tela). **Fatia 10** (Go Live, `v0.15.5`) também não mudou o backend (FASE 9 já estava pronta) — `stores/goLiveStore.ts` novo (`livekit-client` oficial) + `VoicePanel.tsx` integrando os controles; achou e corrigiu um bug real de CSP que bloqueava qualquer conexão ao LiveKit (ver item 9 abaixo e `docs/media.md`). **Fatia 11** (empacotamento/distribuição, `v0.16.0`, encerra a FASE 11 inteira) — `electron-builder` (`^26.15.3`) gera um instalador NSIS real (`desktop/electron-builder.yml`); ícone próprio criado do zero (`desktop/build/icon.ico`/`icon.png`, não existia nenhum antes). Só Windows por enquanto — é a única plataforma testável neste ambiente e a que os ~20 usuários do deploy de fato usam; macOS/Linux ficam pra quando (e se) fizer sentido, é só estender o mesmo `electron-builder.yml` com blocos `mac`/`linux`. Sem assinatura de código (precisa de certificado pago, fora de escopo) e sem auto-update (não pedido, mecanismo de publish do electron-builder nem foi configurado) — instalador roda localmente, sem depender de conta/servidor nenhum, e o Windows vai mostrar aviso de "editor desconhecido" no primeiro uso (SmartScreen), o que é esperado pra um instalador não assinado. **Fatia 12** (`v0.17.0`, não planejada originalmente — descoberta ao criar o servidor único de verdade pra esse deploy): faltava qualquer jeito de **entrar** num servidor existente pelo cliente. "Criar servidor" sempre esteve fora de escopo (item 8 abaixo), mas "entrar via convite" nunca tinha sido discutido nem construído em nenhuma fatia anterior — só apareceu como lacuna real ao tentar efetivamente colocar as ~20 pessoas dentro do servidor "TORA DOS BURRO" (criado direto via API, dono = conta real do usuário, token gerado pelo próprio código de auth do backend sem tocar em senha nenhuma). Backend não mudou (`GET /invites/:code` e `POST /invites/:code/join` já existiam e já eram testados desde a FASE 3) — só ligou o cliente: botão "+" verde no `ServerSidebar` (ao lado dos ícones de servidor) abre um modal (`JoinServerDialog.tsx`, no mesmo estilo do `ScreenSharePicker.tsx`) com um campo pro código; erros do backend (`not found`/`expired`/`max_uses_reached`/`banned`/`already_member`) traduzidos pra mensagens claras, mesmo padrão do 403 de criar canal.
5. **Bug de build corrigido na fatia 5, mas existia desde a fatia 1**: preload sandboxado (`sandbox: true`) não aceita ESM — precisa compilar como CommonJS (`output: { format: 'cjs' }`). Sem isso, `window.api` nunca existia de verdade dentro do Electron real (só parecia "esperado" estar ausente porque toda verificação anterior rodava numa aba de navegador comum, sem preload nenhum). Achado e corrigido só na fatia 5 porque foi a primeira vez que a verificação rodou contra a janela Electron de verdade (via CDP/`--remoteDebuggingPort`) em vez do browser pane. Ver `docs/media.md` e `docs/security.md` para os detalhes.
6. **Dois bugs reais de WebRTC corrigidos na fatia 6** (câmera): um sobre criação antecipada de transceivers colidindo com *glare* na negociação inicial, outro (mais sutil) sobre `presence.onLeave` derrubando peer connections ativas por causa de uma corrida assíncrona no `Phoenix.Presence.handle_diff/2` — nenhum dos dois apareceu nas fatias 4/5 porque só se manifestam com múltiplas tracks de vídeo trocando de estado em sequência. Ver `docs/media.md` (seção "Fluxo de vídeo") para a causa raiz completa de cada um.
7. **FASE 8 revisada logo após a fatia 6**: limite de 1 compartilhamento de tela por vez removido (`v0.15.1`) a pedido explícito do usuário, que definiu o escopo real de deploy deste app — **um único servidor, uso privado por ~20 pessoas conhecidas, nunca público**. O motivo original do limite (cada compartilhamento simultâneo é mais uma faixa de vídeo que todo peer do mesh precisa decodificar) continua tecnicamente válido e não foi resolvido, só aceito conscientemente dado esse escopo — não é uma mudança segura de generalizar para um deploy público ou salas maiores. O cap de vídeo por câmera (4 simultâneos) foi mantido como estava — a revisão foi só pra compartilhamento de tela. Ver `docs/media.md` ("Limites do mesh").
8. **Escopo do deploy confirmado pelo usuário após a fatia 6**: um único servidor, uso privado por ~20 pessoas conhecidas, nunca público (mesma decisão do item 7). Consequências registradas aqui: **Amigos/DM** (item 2) e **FASE 10** (gestão avançada de arquivos, item 1) saem do que está planejado — sem múltiplos servidores, DM entre servidores diferentes não faz sentido, e sem usuários desconhecidos/externos, os endurecimentos de FASE 10 (cotas, CDN, upload retomável em escala) não têm motivo. **"Criar servidor" no cliente também sai de escopo** — o servidor único já existe, criado direto via API; "criar canal" (dentro dele) continua como trabalho válido, é um recurso menor e independente. Anexos **leves** (FASE 4, ainda pendente — precisa de Docker/MinIO) não foram excluídos, só a versão avançada (FASE 10).
9. **Bug real de CSP corrigido na fatia 10 (Go Live)**: a `Content-Security-Policy` do cliente (`desktop/src/renderer/index.html`) nunca liberava `connect-src` para a URL do LiveKit — nenhum host, nem um esquema genérico — então `room.connect()` do `livekit-client` falhava **sempre**, em qualquer ambiente (não só aqui, sem Docker), com uma mensagem genérica indistinguível de "servidor fora do ar". Só apareceu inspecionando o console do DevTools ao vivo (evento `securitypolicyviolation`), não em `npm run typecheck` nem lendo o código — a própria razão de o processo exigir teste ao vivo, não só checagem estática. Como a URL do LiveKit é dinâmica (entregue pelo backend em runtime via `LIVEKIT_URL`, nunca fixa no build do cliente), a correção libera esquemas (`ws:`/`wss:`/`http:`/`https:` para o `:7880` local + `wss:`/`https:` genéricos para produção), não um host específico. Ver `docs/media.md` (seção "Fluxo do Go Live") para o detalhe completo, incluindo o segundo bloqueio (preflight HTTP `.../validate`) descoberto ao corrigir o primeiro.
10. **FASE 18 iniciada informalmente: primeiro deploy real numa VPS (Dokploy), `v1.0.1`**. Backend rodando de verdade em `http://2.28.229.48` (Docker/Dokploy, sem domínio/TLS ainda — decisão explícita pra essa primeira subida) com Postgres gerenciado; cliente reconstruído apontando pra lá (`desktop/.env.production`, novo). **Três bugs reais só visíveis num deploy de verdade** (nenhum apareceu em nenhum ambiente anterior, incluindo os `mix test`/`npm run typecheck` de todas as fases):
    - `rel/overlays/bin/{server,migrate}` (gerados por `mix phx.gen.release --docker`, fatia 11) foram commitados sem o bit de execução Unix — gerados no Windows, onde esse conceito nem existe. O container falhava a cada tentativa com `permission denied` num `exec` que nunca chega a rodar nenhuma linha do BEAM, então nenhum log da aplicação aparecia — só o log de infraestrutura do próprio Docker Swarm (achado trocando os logs do Dokploy de "Native" pra "Swarm"). Corrigido com `git update-index --chmod=+x`.
    - `config/prod.exs` tinha `force_ssl` ligado desde o scaffold original da FASE 1, nunca revisitado — todo pedido HTTP virava 301 pra um `https://` que não existe nesse deploy sem TLS. Corrigido excluindo o IP da lista `exclude: [hosts: [...]]` que já existia (mesmo mecanismo usado pra localhost/127.0.0.1), não desligando `force_ssl` inteiro.
    - O servidor "TORA DOS BURRO" + convite criados antes (fatia 12, ao testar "entrar em servidor") tinham sido criados no Postgres **local** de desenvolvimento, não no Postgres novo da VPS — bancos completamente separados. O cliente apontando pra produção não via nada disso; só ficou claro ao ver, pelo histórico de rede do próprio cliente instalado, que um convite antigo respondia "não encontrado". Recriados direto contra a produção.
    - Também descoberto: já existia um projeto "TORA" nesse mesmo Dokploy, de uma tentativa anterior separada (repositório "Discord2", não `tora-dos-burro`) — deixado intocado, o deploy novo foi pra um projeto Dokploy à parte.
11. **coturn (TURN) implantado na VPS**, como serviço Dokploy Compose separado (`coturn`, Compose Type **"Docker Compose"**, não "Stack"/Swarm — resolve de vez a dúvida da nota anterior: rodando via `docker compose` puro, `network_mode: host` funciona exatamente igual ao dev local, sem nenhuma das limitações de rede do Swarm para a faixa larga de portas UDP que o TURN precisa). Fonte: `docker/coturn/docker-compose.prod.yml` + `docker/coturn/turnserver.prod.conf` (ambos commitados, sem segredo nenhum neles — `TURN_SECRET` só existe na aba Environment desse serviço no Dokploy, igual ao do `backend`).
    - **Quarto bug real só visível no deploy**: a primeira tentativa passou toda a configuração como flags soltas de linha de comando (`-n` + uma lista longa de flags, sem arquivo de config montado). O container entrou em loop de reinício (exit 255) — o `docker-entrypoint.sh` da imagem oficial faz `exec turnserver` com esses argumentos, e algum deles não bateu com o que o `getopt_long` do turnserver esperava, fazendo ele despejar o próprio texto de `--help` inteiro e sair, sempre, a cada reinício. Corrigido movendo quase tudo pra um `turnserver.prod.conf` montado (mesmas diretivas já usadas sem problema em dev desde a FASE 6, passando pelo parser de arquivo, não pelo de CLI) e reduzindo a superfície de CLI a um único override: `-c <path> --static-auth-secret=${TURN_SECRET}`.
    - **Verificado de verdade, não só "container rodando"**: um STUN Binding Request (RFC 5389) manual confirmou o processo respondendo na porta pública; um handshake completo de TURN Allocate com credencial de longo prazo (mesmo algoritmo de `ToraDosBurro.Turn` — usuário/senha efêmeros via HMAC, chave MD5(user:realm:senha), MESSAGE-INTEGRITY) confirmou autenticação E alocação de relay funcionando (`2.28.229.48:51411`, dentro da faixa default 49152-65535 do RFC 5766) — contra o IP público real, não só um check interno do container. `external-ip` não foi necessário (a VPS tem IP público direto na interface, sem NAT).
12. **Onboarding simplificado a pedido do usuário, `v1.0.2`**: três mudanças no fluxo de conta, todas verificadas ao vivo contra produção via o app empacotado de verdade (CDP no processo instalado), não só teste automatizado.
    - Cadastro já autenticava automaticamente — nenhuma mudança de código, só confirmado (o texto da tela de cadastro já dizia isso desde a fatia 5/6 da FASE 11).
    - Login passou a aceitar só usuário + senha. Decisão explícita do usuário: **manter** o comportamento de username poder se repetir (não forçar único) — `Accounts.authenticate_user/2` novo resolve por conta própria quando só existe uma conta com aquele nome; quando há mais de uma, responde `:ambiguous_username` (422) e o cliente (`LoginPage.tsx`) revela um campo de código só nesse caso, sem nunca tentar a senha contra várias contas pra adivinhar qual é.
    - Cadastro entra automaticamente no servidor único — `DEFAULT_SERVER_ID` (env var opcional, configurada em produção com o id do servidor "TORA DOS BURRO" real) + `Servers.join_server/2`, que já existia desde a FASE 3. Botão de entrar por convite deixado no cliente (não atrapalha, pode ser útil se um dia existir um segundo servidor).
    - Verificação ao vivo real (não só `mix test`): registro via `curl` contra `http://2.28.229.48` confirmando token imediato; login só com usuário via `curl`; e o instalador `v1.0.2` de verdade instalado e dirigido via CDP (`--remote-debugging-port`) confirmando na UI real — ícone do servidor aparecendo sem convite, e o campo de código de fato aparecendo só quando duas contas de teste tinham o mesmo nome.
13. **Bug real achado pelo usuário na v1.0.2, corrigido na `v1.0.3`: voz/chat em tempo real nunca conectava de verdade contra produção pelo app empacotado** — ficava preso em "Conectando…", WebSocket sempre rejeitado com 403. Causa: `check_origin` do Phoenix (default `true`) nunca foi desligado em produção — só existe em `dev.exs`, e isso é boilerplate genérico do `mix phx.new`, sem relação nenhuma com o Electron; ninguém tinha de fato testado voz do app empacotado contra a VPS real antes (toda verificação anterior de voz/chat do cliente rodou contra `localhost:4000`). O `Origin` que o Electron empacotado manda (carregando de `file://`) nunca bate com o host configurado — um cliente de WebSocket comum sem header `Origin` nenhum passa direto, por isso nenhum teste de protocolo cru pegou isso antes. Corrigido com `check_origin: false` só no transporte `/socket` (não no `/live`) em `endpoint.ex` — `UserSocket.connect/3` já autentica só por token Guardian no query param, nunca cookie de navegador, então a proteção que `check_origin` oferece (contra site malicioso usando sessão de navegador) nem se aplica a esse cliente.
    - **Achado investigando o mesmo relato, endurecimento relacionado**: o cliente nunca renovava o access token (dura 15min) durante a sessão, só no boot — uma sessão de voz/chat aberta por muito tempo, se o socket precisasse reconectar por qualquer motivo (rede, um deploy no servidor), ficava presa reconectando pra sempre com o token velho. `authStore.ts` agora renova a cada 10min; `socket.ts` usa uma função pra `params` (token sempre atual) em vez de um valor fixo desde a conexão original — sem derrubar uma conexão saudável só pra atualizar o token.
    - Verificado contra o bug real do usuário: extraí o token da sessão travada dele (`window.api.secureStorage`), confirmei que `/users/me` aceitava mas o handshake de WebSocket cru rejeitava com 403 — descartando a hipótese inicial (token expirado) e apontando pro `check_origin`. Depois do fix, testei de novo do zero (conta nova, app empacotado `v1.0.3` de verdade via CDP): painel de voz conecta e mostra os controles reais (mutar/ensurdecer/câmera/tela). O único erro que sobra é do Go Live tentando conectar num LiveKit que não existe (`livekit.placeholder.invalid`) — limitação já conhecida e documentada, sem relação com esse bug.
14. **Identidade visual própria, `v1.0.4`** — pedido do usuário ("interface bonita, gamer"), deliberadamente fugindo do roxo-neon-em-preto que qualquer gerador cairia por padrão. Sistema definido em `desktop/src/renderer/src/index.css` (tokens via `@theme` do Tailwind v4): fundo quase-preto com leve tom azul-violeta, dupla de acento com significado (volt = verde-limão elétrico, estado positivo/ativo; plasma = magenta, estado quente/ao vivo/perigo — não um acento neon genérico só), tipografia técnica (Chakra Petch/Manrope/JetBrains Mono), corte chanfrado no canto superior direito como assinatura estrutural repetida em superfícies grandes. Elemento de assinatura: no painel de voz, quem está com o microfone aberto ganha um contorno com glow pulsante ("microfone quente") — ligado ao estado real da chamada, não só decoração. Nenhuma mudança de funcionalidade, só `index.css` + todos os componentes/páginas do `desktop/`.
    - **Achado no build de produção (não em dev)**: `@import url(...)` pro Google Fonts dentro do CSS violava a regra de que `@import` precisa ser a primeira regra — o Lightning CSS do build de produção sinalizava isso (dev não, o Vite trata CSS diferente em dev). Corrigido trocando por um `<link rel="stylesheet">` em `index.html` — mais robusto de qualquer forma, não depende de ordem de regras CSS. CSP (`connect-src`/`style-src`/`font-src`) estendida pra `fonts.googleapis.com`/`fonts.gstatic.com`, mesma classe de gotcha já documentada nesse projeto pro LiveKit.
    - Verificado ao vivo: dev server real com estado autenticado forçado via import dinâmico dos stores (técnica já estabelecida no projeto) pra ver todas as telas sem precisar de backend, e depois o instalador `v1.0.4` de verdade — instalado, rodando, capturado via `Page.captureScreenshot` do protocolo CDP (não só `Runtime.evaluate` como nas verificações anteriores).
15. **Moldura da janela personalizada, `v1.0.5`/`v1.0.6`** — dois pedidos seguidos do usuário. `v1.0.5`: `Menu.setApplicationMenu(null)` tira a barra File/Edit/View/Window que o Electron gera sozinho sem isso (nenhuma das ações faz sentido pra esse app). `v1.0.6`: janela sem moldura nativa nenhuma ("borda infinita") — `frame: false` na `BrowserWindow` + `TitleBar.tsx` novo desenhando barra de título/minimizar/maximizar-restaurar/fechar do zero, no mesmo sistema visual (bevel, volt, tipografia técnica), agindo via IPC novo (`window.api.windowControls.*`) porque o renderer nunca pode mexer na própria janela sozinho.
    - **Verificação exigiu um método novo**: menu e moldura de janela são chrome nativo do SO, não fazem parte do DOM da página — nem o Browser pane nem `Page.captureScreenshot` via CDP mostram isso (só capturam a área de conteúdo). Usado `GetWindowRect`/`CopyFromScreen` via PowerShell pra tirar um print da janela real inteira, e cliques de verdade nos 3 botões custom confirmando efeito real (`IsIconic` pra minimizar, tamanho da janela mudando pra maximizar, porta do CDP parando de responder — processo encerrado de verdade — pro fechar), não só que o handler disparou.
16. **Voz e compartilhamento de tela no estilo Discord, `v1.0.7`** — quatro pedidos do usuário juntos:
    - Clicar num canal de voz já entra direto (sem botão "Conectar" separado) — `HomePage.tsx` decide isso no `onSelect`, comparando com o canal de voz atualmente conectado pra não reentrar à toa.
    - Lista de participantes (ícone + nome) aparece embaixo do canal de voz na barra lateral — recorte deliberado: só do canal em que a pessoa **realmente está conectada**, não uma prévia de canais não-joinados (isso pediria um mecanismo novo de presença no backend, fora de escopo desse pedido).
    - **Indicador de fala de verdade** (`webrtc/SpeakingDetector.ts`, novo) — um `AnalyserNode` por stream (mic local + cada peer remoto). Primeira tentativa usava a média de amplitude no domínio da **frequência** (`getByteFrequencyData`) e falhava: testado ao vivo com um tom sintético puro (oscillator), a energia toda ficava concentrada em 2-3 bins de frequência, e a média com os outros ~250 bins (quase todos zero) afogava completamente o sinal — mesmo com o tom bem alto, a média nunca cruzava o limiar. Corrigido usando RMS no domínio do **tempo** (`getByteTimeDomainData`), que mede volume de verdade (o quanto a onda se afasta do centro) independente de quantas frequências o som ocupa. Confirmado depois do fix: RMS ≈ 81 com o tom alto, RMS = 0 em silêncio.
    - Qualidade do compartilhamento de tela (720p/1080p/1440p, 30/60 FPS) — `ScreenSharePicker.tsx` ganha os seletores, aplicados como constraints `ideal` (não `exact`, pra não falhar o compartilhamento inteiro numa tela física menor que o pedido) no `getDisplayMedia`.
    - Grade com destaque quando 2+ pessoas compartilham tela ao mesmo tempo — `ScreenShareGrid` novo em `VoicePanel.tsx`: uma tela grande em foco + tira de miniaturas clicáveis: a pessoa escolhe quem fica em evidência. Só aparece com mais de 1 compartilhamento simultâneo (uma tela só continua como antes, sem grade).
    - **Verificado ao vivo com duas contas reais simultâneas** (app empacotado de verdade, `--use-fake-device-for-media-stream` + `--user-data-dir` separado por instância, técnica nova nesse projeto): entrar direto confirmado nos dois lados; roster confirmado nos dois lados; indicador de fala confirmado via tom sintético (o áudio falso padrão do Chromium sozinho não era alto o suficiente pra cruzar o limiar — substituí `getUserMedia` por um oscillator alto via `Runtime.evaluate` pra validar o pipeline de verdade, sem precisar de microfone físico); qualidade confirmada lendo `getSettings()` da track capturada de verdade (`2560x1440 @ 60fps`, exatamente o pedido); troca de foco na grade confirmada com dois compartilhamentos reais simultâneos, um de cada instância.
17. **Trocar a qualidade da tela já transmitindo + tela compartilhada responsiva, `v1.0.8`** — dois pedidos do usuário juntos:
    - `voiceStore.ts` ganha `updateScreenShareQuality(quality)`, acionada por um novo `ScreenShareQualityMenu` (popover ao lado de "PARAR TELA" em `VoicePanel.tsx`, reaproveitando os mesmos `RESOLUTIONS`/`FRAME_RATES` do `ScreenSharePicker.tsx`, agora exportados). Recaptura a mesma fonte (`desktopCapturer` source id, guardado em `lastScreenSourceId`) nos novos parâmetros e entrega a track nova pro `mesh.setScreenTrack()` já existente — mesmo caminho de `replaceTrack` que o início do compartilhamento e a troca de câmera já usam, então não renegocia nem manda evento novo pro servidor.
    - **Bug real achado e corrigido no processo**: a primeira versão pedia a nova captura (`getDisplayMedia`) *antes* de parar a antiga. Do lado de quem compartilha, tudo parecia certo (track nova, sem erro, `connectionState: connected`) — mas `getStats()` no `RTCRtpSender` (`outbound-rtp`) provou que o encoder continuava mandando a resolução **antiga**, com `qualityLimitationReason: "none"` (descartando adaptação por banda/CPU como causa): o Chromium, com a captura anterior daquela mesma fonte ainda viva no momento do pedido, reaproveita a sessão já em andamento e ignora os parâmetros novos por completo. Corrigido invertendo a ordem — para a track atual antes de pedir a próxima; se a recaptura falhar depois disso, não dá mais pra manter o compartilhamento anterior rodando, então o código chama o mesmo `stopScreenShare()` de sempre (limpeza completa, incluindo avisar o servidor) em vez de deixar um estado "compartilhando" com uma track morta.
    - De quebra, o vídeo da tela compartilhada (single view e o destaque da grade) ganhou um prop `large` no `RemoteVideo` de `VoicePanel.tsx` — troca o teto de `max-w-2xl` (672px, mesmo limite usado pra câmera/Go Live) por preencher a largura do painel. Escopo deliberado: só a tela compartilhada, não os outros tipos de vídeo, seguindo a reclamação específica do usuário.
    - **Verificado ao vivo com duas contas reais na mesma chamada de voz**: troquei a qualidade várias vezes em sequência (720p30 → 1440p60 → 1080p30, depois de volta pra 720p30) e, a cada troca, conferi não só o que a track local dizia ter (`getSettings()`), mas o tamanho real do frame **decodificado** do lado de quem recebe (`videoWidth`/`videoHeight` do elemento de vídeo) — confirmando que o vídeo muda de verdade pro outro lado, nos dois sentidos, sem cair a chamada. Também testado clicando de verdade no popover novo (não só chamando a store direto). Achado incidental do processo de teste (não é bug do app): reimportar os módulos da store por `import()` dinâmico depois de uma edição em dev, sem recarregar a página, pode pegar uma cópia duplicada do módulo (efeito colateral do versionamento de URL do HMR do Vite) — contornado testando sempre a partir de uma instância recém-aberta depois de qualquer edição de código, não só um `location.reload()`.
18. **Bug real reportado pelo usuário logo após a v1.0.8, corrigido na `v1.0.9`**: o `ScreenShareQualityMenu` novo fechava sozinho enquanto a pessoa arrastava o mouse pra cima em direção à opção desejada — sem tempo de clicar. Causa: fechava no `onMouseLeave` do `<div className="relative">` que envolve botão + popover, mas o popover é `position: absolute` — isso o tira do fluxo normal, então a caixa desse `div` não se estende até cobrir o vão visual entre o botão e o popover (só o botão, seu único filho em fluxo normal, contribui pro tamanho do contêiner); ao cruzar esse vão pra alcançar uma opção, o cursor passava por cima de algo que não é o contêiner nem o popover, disparando `mouseleave` cedo demais. Corrigido trocando o fechamento por clique-fora (`mousedown` no `document` + `ref`, fecha se o alvo não está dentro do contêiner) em vez de depender de hover — elimina essa classe inteira de bug e é o padrão mais comum pra esse tipo de menu de qualquer forma.
    - **Verificação exigiu simular o gesto exato relatado, não só um clique**: `element.click()`/`dispatchEvent()` via JS não reproduzem o bug (o navegador só calcula `mouseenter`/`mouseleave` "de verdade" a partir de movimento real do ponteiro, não de eventos sintéticos disparados em script) — usado `Input.dispatchMouseEvent` do protocolo CDP (mesmo mecanismo por trás de ferramentas de automação de UI) pra mover o mouse em vários passos pequenos do botão até uma opção, atravessando exatamente o vão do bug, e só então clicar. Confirmado que o clique registrava (a qualidade realmente mudava) e que clicar fora ainda fechava o menu normalmente.

## Processo de desenvolvimento (regras do projeto, mantidas)

1. Não escrever código gigante de uma vez.
2. Implementar uma funcionalidade por vez.
3. Antes de implementar, explicar: objetivo, arquivos envolvidos, arquitetura, dependências, fluxo de dados.
4. Depois implementar.
5. Depois criar testes.
6. Depois explicar como executar.
7. Não inventar APIs ou bibliotecas.
8. Verificar compatibilidade entre versões.
9. Não adicionar dependências sem justificar.
10. Não criar microsserviços prematuramente.
11. Separar Control Plane / Media Plane / Data Plane.
12. Priorizar código simples, modular e sustentável.

Formato de resposta durante o desenvolvimento (a partir da FASE 1): Etapa atual → Objetivo → Arquitetura → Arquivos → Implementação → Banco de dados → Testes → Como executar → Como testar → Próxima etapa (só a próxima, nunca várias fases de uma vez).
